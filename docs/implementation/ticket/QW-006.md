# QW-006 — Screen navigation stack

Implements navigation between S-01, S-02, S-03 with param passing, back navigation, and return-target logic after save/cancel.

**Contract:** currentScreen: {screen: 'S-01'|'S-02'|'S-03', taskId?: string, mode?: 'add'|'edit'}; navigateTo(screen, params): void; goBack(): void

## Why

The user needs to navigate between the day view, add/edit task, and task detail screens with correct back navigation and return-target logic, per REQ-FUNC-009.

## What

A navigation stack module exposing currentScreen state, navigateTo(screen, params) for forward navigation with parameters, and goBack() for returning to the appropriate prior screen.

## Scope

**In:** currentScreen state object, navigateTo with screen id and params (taskId, mode), goBack stack logic, return-target determination after save/cancel

**Out:** Date state management, task CRUD operations, UI rendering of individual screens, delete confirmation UI

## Tasks

- [ ] **T1** — Initialize the navigation module with currentScreen set to { screen: 'S-01' } and an empty navigation stack _(verify: On instantiation, currentScreen equals { screen: 'S-01' } with no taskId or mode)_
- [ ] **T2** — Implement navigateTo(screen, params) to push the current screen onto the stack and set currentScreen to the target screen with provided params _(verify: From S-01, calling navigateTo('S-02', { mode: 'add' }) sets currentScreen to { screen: 'S-02', mode: 'add' }; calling navigateTo('S-03', { taskId: 't1' }) sets currentScreen to { screen: 'S-03', taskId: 't1' })_
- [ ] **T3** — Implement goBack() to pop the navigation stack and restore the prior currentScreen, defaulting to S-01 if the stack is empty _(verify: After navigating S-01 -> S-02 -> S-03, calling goBack() restores S-02; calling goBack() again restores S-01; calling goBack() from S-01 stays on S-01)_
- [ ] **T4** — Wire navigateTo('S-02') from S-01 add button with mode 'add' so it routes to the add/edit screen without a taskId _(verify: Navigating from S-01 via add button results in currentScreen { screen: 'S-02', mode: 'add' } with no taskId)_
- [ ] **T5** — Wire navigateTo('S-02') from S-03 Edit action with mode 'edit' and the current task's taskId so the add/edit screen is pre-populated _(verify: Navigating from S-03 via Edit results in currentScreen { screen: 'S-02', mode: 'edit', taskId: '<selected task id>' })_
- [ ] **T6** — Implement return-target logic so goBack() after Save or Cancel on S-02 returns to the screen that initiated the navigation (S-01 or S-03) _(verify: S-01 -> S-02 then goBack returns to S-01; S-01 -> S-03 -> S-02 then goBack returns to S-03)_
- [ ] **T7** — Implement delete-confirmation return logic so that after confirming deletion on S-03, navigation returns directly to S-01 clearing the stack _(verify: From S-03, after delete confirmation, currentScreen becomes { screen: 'S-01' } and the navigation stack is empty)_

## Acceptance

- Given the user is on the day view screen S-01, when the user activates the add button, then the system navigates to the Add/edit task screen S-02.
- Given the user is on the day view screen S-01, when the user selects a task in the list, then the system navigates to the Task detail screen S-03 for that task.
- Given the user is on the Task detail screen S-03, when the user activates the Edit action, then the system navigates to the Add/edit task screen S-02 pre-populated with that task's data.
- Given the user is on the Add/edit task screen S-02, when the user activates Save or Cancel, then the system navigates back to the appropriate prior screen.
- Given the user is on the Task detail screen S-03, when the user activates the Delete action, then the system prompts for confirmation and upon confirmation navigates back to the day view screen S-01.
- _(unit)_ The navigation stack correctly preserves the full prior-screen history for multi-step journeys such as S-01 -> S-03 -> S-02
- _(unit)_ goBack() from S-01 is a safe no-op that leaves currentScreen unchanged
